03 — Defect case study

Workforce disappeared when population changed

LaborDistributorManager distributes Farmers, Workers and Engineers among factories inside each region. The first implementation incrementally added and subtracted labor. Manual testing exposed that this approach could no longer determine how much a factory should return or borrow when the population or factory list changed.

Observed

Accounting drift

  • Labor could disappear or be duplicated after redistribution.
  • Factories retained allocations calculated from an outdated population.
  • Production efficiency no longer matched the workforce currently available.
Root cause

Incremental mutation without a reliable baseline

Each update depended on the previous local add/subtract operations. Once several factories and population changes were involved, there was no single trustworthy value from which to calculate the next distribution.

Resolution

Refund, recompute, then lend again

The redesigned model stores the previous lend, restores it before calculation, derives a new regional utilization ratio, broadcasts that ratio to every factory in the bucket and records the replacement lend.

Recomputation model

The previous allocation becomes part of the calculation—not hidden state

  1. 01

    Group factories by region and labor type, then sum their required labor.

  2. 02

    Recover the real available population by adding the previous lend back to the currently visible amount.

  3. 03

    Calculate one utilization ratio: available labor divided by total demand, clamped from 0% to 100%.

  4. 04

    Send the same ratio to every factory in that regional labor bucket.

  5. 05

    Lend the newly required amount and record it for the next recomputation.

// LaborDistributorManager.cs
int availableNow =
    RegionResourceManager.Instance
        .GetAmount(regionID, resType);

int prevLend = lastLendMap
    .TryGetValue(laborType, out var prev)
    ? prev : 0;

int availableBeforeLend =
    availableNow + prevLend;

float ratio = totalReq == 0
    ? 0f
    : Mathf.Clamp01(
        availableBeforeLend / (float)totalReq);

foreach (var entry in factories)
    entry.factory.OnLaborRatioUpdated(ratio);

RegionResourceManager.Instance
    .LendInRegion(regionID, resType, totalReq);

lastLendMap[laborType] = totalReq;
// RegionResourceManager.cs
int previousLend = lendDict.ContainsKey(type)
    ? lendDict[type] : 0;

res[type] += previousLend; // refund old lend
res[type] -= newLendAmount; // apply replacement
lendDict[type] = newLendAmount;

LendInRegion contract

Replacement is safer than incremental correction

LendInRegion does not try to calculate a difference from scattered factory state. It returns the complete previous lend and applies the complete new lend as one replacement operation, preserving workforce accounting across repeated changes.

If the population later rises to 16, the old lend is restored first and the whole bucket is recalculated to 80%. If a factory is removed, demand is recalculated and the surplus returns to the regional pool.

Tests I would formalize from the defect today

06 — QA reflection

What this process taught me—and what I would change

The iterative process helped me find state-management defects that were difficult to predict from code alone. It also showed the limitations of testing my own implementation without retained evidence or an independent reviewer.

01

Retain test artifacts

Write acceptance criteria, test scenarios and execution results before closing a feature.

02

Track the defect lifecycle

Record reproduction steps, expected/actual results, severity, evidence, fix version and confirmation status.

03

Create a regression checklist

Re-run high-risk interactions between population, labor, storage, production and save/load for every build.

04

Extract testable simulation logic

Move workforce accounting into engine-independent classes and automate boundary and state-transition tests.

The strongest lesson was that dynamic systems should be recalculated from a reliable source of truth instead of corrected through accumulated local mutations. The same principle now guides how I design both software and test coverage.

Case study

A small first AWS project with a complete delivery path

ShortURL accepts an HTTP or HTTPS address, creates a cryptographically generated Base62 code, persists the mapping and returns a reusable short link. Opening that link follows a cache-first lookup path designed to reduce repeated database reads.

01 — Core request flows

Creation writes once; redirects favor the fastest available source

The service keeps link creation and link resolution deliberately small. MySQL remains the durable source of truth, while Valkey accelerates frequently requested codes and can fail without making stored links unavailable.

POST/api/links

Create a short link

  1. 01

    Validate and normalize an HTTP or HTTPS URL up to 2,048 characters.

  2. 02

    Generate a seven-character Base62 code with cryptographic random bytes and no modulo bias.

  3. 03

    Insert the mapping into MySQL and retry on a rare duplicate-code collision.

  4. 04

    Warm the cache, then return HTTP 201 with the short code, short URL and original URL.

GET/{code}

Resolve and redirect

  1. 01

    Reject malformed codes before touching cache or database.

  2. 02

    Read Valkey using the namespaced key short-url:{code}.

  3. 03

    On a miss or cache outage, query MySQL and repopulate the cache when found.

  4. 04

    Return HTTP 302 to the original address, or redirect to the 404 page when no mapping exists.

↻

Cache acceleration without cache dependency

Cache read and write failures are logged and skipped. A cache outage therefore increases database traffic but does not invalidate links already stored in MySQL.

02 — Short-code generation

Base62 keeps the code URL-safe while cryptographic randomness avoids predictable sequences

The generator draws bytes from Node’s crypto module and maps accepted values to digits, uppercase letters and lowercase letters. Values from 248 to 255 are discarded so all 62 characters have the same probability.

248uniform byte cutoff
5×maximum collision retries
src/utils/generate-code.js

Rejecting biased bytes

Using byte modulo 62 directly would make several characters slightly more likely. Rejecting the incomplete range preserves a uniform distribution without introducing a third-party ID library.

while (result.length < length) {
  const bytes = crypto.randomBytes(
    length - result.length
  );

  for (const byte of bytes) {
    if (byte >= 248) continue;
    result += ALPHABET[byte % 62];
    if (result.length === length) break;
  }
}

The database remains the collision authority

The short code is the MySQL primary key. If an insert returns ER_DUP_ENTRY, the service generates a new value and retries. After five failed attempts it returns a controlled 503 instead of overwriting an existing mapping.

03 — Cache-aside resolution

Valkey improves the hot path but never becomes the source of truth

Every redirect begins with the namespaced cache key short-url:{code}. The service queries MySQL only on a miss, then warms the cache with a configurable TTL. Cache connection errors are logged and treated as misses.

HIT

Cache hit

Return the stored URL and mark the response source as cache.

MISS

Cache miss

Read MySQL, cache the record for the next request and redirect.

DEGRADED

Valkey unavailable

Skip the failed cache operation and continue through MySQL.

404

Code not found

Redirect to /404 when the durable store has no matching record.

05 — Runtime operations

Health reporting preserves redirect availability when only the cache is down

The /health endpoint checks MySQL and Valkey separately. Database failure makes the target unavailable, while cache failure reports a degraded but HTTP-200 state so the load balancer can continue sending traffic to a service that can still resolve links.

200

OK

MySQL up, Valkey up — full data path available.

200

DEGRADED

MySQL up, Valkey down — redirects continue through the database.

503

UNAVAILABLE

MySQL down — durable reads and writes cannot be guaranteed.

Graceful container shutdown

SIGTERM closes the HTTP server first, then ends the MySQL pool and Valkey client with Promise.allSettled. A ten-second fail-safe prevents the task from hanging during replacement. CloudWatch retains application logs for seven days and ECS Container Insights is enabled.

07 — Engineering reflection

The design is intentionally small; its boundaries make the next improvements clear

ShortURL was my first AWS project, so the implementation prioritizes an understandable end-to-end path over production scale. The current code demonstrates clean fallbacks and reproducible infrastructure while documenting the cost and availability compromises made for a temporary demo.

01

What is already strong

Stateless application logic, prepared SQL statements, cryptographic code generation, graceful cache failure, scoped network access and runtime secret injection.

02

Demo-cost decisions

No NAT Gateway, one RDS instance, one Valkey node, no backups and delete-on-stack-removal policies reduce temporary cost but also reduce resilience.

03

Public-edge gap

04

Production evolution

Add rate limiting and abuse protection, ECS autoscaling, Multi-AZ data services, backups, alarms, private image access through NAT or VPC endpoints and deployment automation.

05 — Data consistency

Stock moves through explicit states instead of one destructive decrement

Inventory keeps quantity_on_hand, quantity_reserved and quantity_sold separately. Each transition executes in a MySQL transaction, locks the affected variant rows and writes an inventory movement linked to the order.

Reserve

Lock available stock during checkout without removing it from on-hand quantity.

Release

Return reserved stock after cancellation, failure or an abandoned workflow.

Commit

Decrease on-hand and reserved quantities when fulfillment begins.

Mark sold

Increase the sold counter when the order reaches its completed state.

Inventory Service/server.js

Row locks prevent two checkouts from spending the same stock

SELECT ... FOR UPDATE serializes changes to each variant inside the transaction. The service checks available quantity before updating reserved stock and commits all requested items together.

Open source file ↗ 
await connection.beginTransaction();

SELECT quantity_on_hand, quantity_reserved
FROM inventory_items
WHERE variant_id = ?
FOR UPDATE;

available = quantity_on_hand - quantity_reserved;
if (available < requested) await connection.rollback();

UPDATE inventory_items
SET quantity_reserved = quantity_reserved + ?;

await connection.commit();

Consistency boundary

  • A local database transaction protects each mutation within Inventory or Order Service.
  • Cross-service checkout is a compensating workflow, not one distributed ACID transaction.
  • Payment Worker checks order_id first and re-publishes the stored result on a sequential redelivery.
  • Six logical schemas currently share one private RDS MySQL primary configured for Multi-AZ availability.
